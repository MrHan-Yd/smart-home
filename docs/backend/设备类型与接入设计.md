# 智能家居子系统 — 设备类型与接入设计

> 目标：**凡 HA 能接入的设备，本系统都能「看见」；控制与展示按类型逐步增强。**  
> 原则：以 HA 为设备源；本系统做 **发现 → 纳入 → 能力映射 → 控制/展示**，类型可插拔扩展。  
> 相关：[功能设计.md](./功能设计.md) · [架构设计.md](./架构设计.md)

---

## 1. 「添加设备」在本系统里指什么

| 步骤 | 在哪里做 | 说明 |
|------|----------|------|
| ① 物理配网 / 厂商绑定 | 米家等厂商 App | **本系统不做** |
| ② 接入 Home Assistant | HA 集成（UI / 配置） | 小米、涂鸦、Matter… 以 HA 支持列表为准 |
| ③ **发现** | 本系统 | 从 HA 拉取 entity 列表，展示「可添加」 |
| ④ **纳入（添加）** | 本系统 | 用户把 entity（或一组 entity）加入「我的设备」 |
| ⑤ 整理 | 本系统 | 房间、显示名、收藏、隐藏 |
| ⑥ 使用 | 本系统 | 按 **能力（capability）** 展示控件与历史 |

因此产品文案建议：

- **「从 HA 同步 / 添加设备」** = 发现 + 纳入  
- **不是**「扫描 Wi‑Fi 添加新硬件」

```
厂商设备 ──配网──► 厂商云/本地
              │
              ▼
        Home Assistant 集成（唯一协议适配层）
              │
              ▼  states / services
        smart-home 发现池（全部 entity）
              │ 用户勾选「添加到我的设备」
              ▼
        我的设备（本地元数据 + entity 绑定）
              │
              ▼
        能力驱动的 UI / 控制 API
```

## 2. 设计目标

| 目标 | 做法 |
|------|------|
| 多类型 | 不写死「只有灯」；用 **HA domain + 能力注册表** 扩展 |
| 先通后强 | 未知类型也能 **列表展示状态**；控制能力按阶段注册 |
| 可演进 | 新增一种设备类型 = 加 capability 映射 +（可选）前端控件，不改主流程 |
| 跟 HA 走 | 类型覆盖面 ≤ HA 已支持集成；HA 没有的本系统也不承诺 |

---

## 3. 核心概念

| 概念 | 定义 |
|------|------|
| **entity** | HA 最小状态单元，`entity_id = {domain}.{object_id}`，如 `light.bedside` |
| **domain** | HA 领域：`light` `switch` `sensor` `climate` `cover` … |
| **发现项（DiscoveryItem）** | 同步自 HA、尚未或已经纳入的候选 |
| **设备（Device）** | 用户「我的设备」中的一条业务记录，绑定 1 个（MVP）或多个 entity |
| **能力（Capability）** | 与 UI/API 对齐的抽象动作与状态，如 `on_off`、`brightness`、`temperature` |
| **类型档案（TypeProfile）** | domain（及可选 device_class）→ 默认能力集 + 展示策略 |

### 3.1 MVP 绑定策略

- **1 Device ↔ 1 primary entity_id**（简单、好实现）  
- 同一物理硬件在 HA 拆成多个 entity（灯 + 功率传感器）时：  
  - P0/P1：当两个设备分别添加，或只添加主 entity  
  - P3：支持「组合设备」（一设备多 entity 绑定）

## 4. 添加设备流程（产品）

### 4.1 发现

1. 用户打开「添加设备」  
2. 后端 `GET HA /api/states`（可缓存）  
3. 过滤规则（可配置）：  
   - 默认隐藏：已在「我的设备」中的 entity  
   - 可选隐藏：`domain` 黑名单（如 `zone`、`person`、部分 `binary_sensor` 噪音）  
   - 可选隐藏：`entity_id` 匹配内部 helper  
4. 列表展示：名称、domain、当前 state、是否已支持「控制」、所在 HA area（若有）

### 4.2 纳入（添加）

| 方式 | 说明 | 阶段 |
|------|------|------|
| 单选添加 | 勾选一个 entity → 创建 Device | P0 |
| 批量添加 | 多选一次添加 | P0～P1 |
| 按 domain 全选 | 「添加全部灯」 | P1 |
| 自动纳入 | 新 entity 出现自动进列表（可关） | P2 |
| 按 HA 设备（device registry）聚合 | 一物理设备多 entity 一次添加 | P3 |

写入本地：

- `entity_id`、`domain`、显示名（默认可取 `friendly_name`）  
- `type_profile` / 解析出的 capabilities 快照（可每次动态算，不必死存）  
- `home_id`、`room_id`（可选）、`sort`、`favorite`、`hidden`

### 4.3 移除

- **从本系统移除** ≠ 从 HA 删除设备  
- 仅删本地 Device 元数据；HA 里实体仍在，可再次添加  

### 4.4 与 HA 侧变更的同步

| HA 变化 | 本系统行为 |
|---------|------------|
| 实体改名（friendly_name） | 列表优先本地 display_name；未自定义则跟 HA |
| 实体消失 / unavailable | 标记离线或「源已删除」，允许用户清理 |
| 新实体出现 | 出现在发现池，不自动打乱「我的设备」（除非开启自动纳入） |

## 5. 类型与能力模型（可扩展核心）

### 5.1 为何用 Capability 而不是写死 if domain == light

- 前端/API 稳定：`action=turn_on`，不关心底层是 light 还是 switch  
- 新 domain：注册表加一行映射即可  
- 同一 domain 能力不同：用 `device_class` / attributes 再细分（如 sensor 温度 vs 电量）

### 5.2 能力目录（Capability Catalog）

| capability_id | 含义 | 典型 state/attrs | 典型 HA service |
|---------------|------|------------------|-----------------|
| `on_off` | 开关 | `on`/`off` | `turn_on` / `turn_off` / `toggle` |
| `brightness` | 亮度 | `brightness` 0–255 | `turn_on` + brightness |
| `color_temp` | 色温 | `color_temp_kelvin` 等 | `turn_on` + color_temp |
| `color_hs` | 彩色 | `hs_color` | `turn_on` + hs_color |
| `open_close` | 开合 | `open`/`closed` | cover `open_cover` / `close_cover` |
| `position` | 位置 0–100 | `current_position` | `set_cover_position` |
| `climate_hvac` | 空调模式 | `hvac_mode` | `set_hvac_mode` |
| `climate_temp` | 目标温度 | `temperature` | `set_temperature` |
| `lock` | 锁 | `locked`/`unlocked` | `lock` / `unlock` |
| `media_play` | 播放控制 | `playing`… | media_player 系列 |
| `numeric_sensor` | 只读数值 | state 数值 + unit | 无控制 |
| `binary_sensor` | 只读通断 | `on`/`off` + device_class | 无控制 |
| `scene_activate` | 场景 | — | `scene.turn_on` |
| `script_run` | 脚本 | — | `script.turn_on` |
| `raw_state` | 兜底只读 | 任意 state | 无控制 |

**未注册 capability 的 domain：仍可添加，仅 `raw_state` 展示。**

### 5.3 Domain → 默认能力（TypeProfile 注册表）

实现上建议代码内注册表（Go map / 配置 YAML），**按阶段启用控制**，展示可先全开。

| HA domain | 默认 capabilities | 控制实现阶段 | 备注 |
|-----------|-------------------|--------------|------|
| `light` | on_off, brightness, color_temp, color_hs* | P0 on_off；P1 其余 | *有 attr 才暴露 |
| `switch` | on_off | P0 | 插座、开关 |
| `input_boolean` | on_off | P0 | HA 辅助 |
| `fan` | on_off,（转速后续） | P1 | |
| `cover` | open_close, position* | P1 | 窗帘、车库门 |
| `climate` | on_off, climate_hvac, climate_temp | P1 | 空调、地暖 |
| `lock` | lock | P1 | 门锁（慎用远程） |
| `media_player` | media_play, on_off | P2 | |
| `vacuum` | on_off 类启停 | P2 | 扫地机 |
| `humidifier` | on_off, … | P2 | |
| `water_heater` | on_off, climate_temp 类 | P2 | |
| `remote` | 按键类（后续） | P3 | |
| `camera` | 预览链接/快照（不做录像中台） | P2 可选 | |
| `sensor` | numeric_sensor | 只读 P0 展示 | device_class 细分单位 |
| `binary_sensor` | binary_sensor | 只读 P0 展示 | 门窗/人体等 |
| `number` / `input_number` | 设数值 | P2 | |
| `select` / `input_select` | 选项 | P2 | |
| `scene` | scene_activate | P2 | 可当「设备」或独立入口 |
| `script` | script_run | P2 | |
| `button` / `input_button` | 一次性 press | P1 | |
| `siren` | on_off | P2 | |
| `valve` | open_close | P2 | |
| `lawn_mower` 等长尾 | raw_state → 逐步加 | 按需 | |
| **未列出 domain** | **raw_state** | 始终可添加展示 | 保证「HA 有就能加」 |

> 表可随 HA 新 domain 追加；**不必一次实现全部控制**。

### 5.4 能力解析规则（运行时）

```
输入：HA state 对象（entity_id, state, attributes）
1. domain = entity_id 的 domain 段
2. profile = Registry[domain] ?? Profile{ caps: [raw_state] }
3. 对 profile 中每个 cap：
   - 若 cap 依赖 attributes（如 brightness）：attributes 无则从 supported 列表移除
   - supported_features 位掩码（light/cover 等）可进一步裁剪
4. 输出：DeviceView { capabilities[], primary_state, ui_hints }
```

前端：**只根据 `capabilities[]` 渲染控件**，禁止写死 `if (domain==='light')` 散落各页（domain 仅用于图标默认映射）。

## 6. 统一控制 API（与类型解耦）

### 6.1 动作模型

```http
POST /api/v1/devices/{deviceId}/actions
Content-Type: application/json

{
  "action": "turn_on",          // 逻辑动作名
  "params": { "brightness": 128 },
  "idempotency_key": "可选"
}
```

| action（逻辑） | 所需 capability | 映射到 HA（示例） |
|----------------|-----------------|-------------------|
| `turn_on` | on_off | `{domain}/turn_on` |
| `turn_off` | on_off | `{domain}/turn_off` |
| `toggle` | on_off | `{domain}/toggle` |
| `set_brightness` | brightness | `light/turn_on` + brightness |
| `set_color_temp` | color_temp | `light/turn_on` + color_temp |
| `open` / `close` / `stop` | open_close | cover 对应 service |
| `set_position` | position | `cover/set_cover_position` |
| `set_hvac_mode` | climate_hvac | `climate/set_hvac_mode` |
| `set_temperature` | climate_temp | `climate/set_temperature` |
| `lock` / `unlock` | lock | `lock/lock` 等 |
| `activate` | scene_activate | `scene/turn_on` |
| `run` | script_run | `script/turn_on` |
| `press` | button | `button/press` |

**服务端：**

1. 校验设备属于当前用户  
2. 校验该设备当前具备对应 capability（防越权乱调）  
3. 查 **ActionMapper**：action + domain → HA service + body  
4. 调 HA；写审计；返回最新视图  

未知 action → 400；无 capability → 409/400；HA 失败 → 502 + 可读信息。

### 6.2 扩展一种新设备类型的步骤（开发清单）

1. 在 **TypeProfile 注册表** 增加 domain → capabilities  
2. 在 **ActionMapper** 增加 action → HA service 映射（若需新动作）  
3. （可选）前端增加专用控件组件；否则用通用 on_off / 滑条 / 只读  
4. （可选）历史：声明该 cap 是否支持曲线（numeric / on_off 时段）  
5. 文档表 §5.3 补一行 + 阶段标记  

**不需要**改添加流程、OAuth、列表主链路。

## 7. 发现与添加 API（摘要）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/discover/entities` | 发现池；query：`domain` `q` `only_new` |
| POST | `/api/v1/devices` | 纳入：`{ "entity_id": "light.xxx", "name": "可选" }` |
| POST | `/api/v1/devices/batch` | 批量 entity_id[] |
| GET | `/api/v1/devices` | 我的设备 + 实时/缓存状态 + capabilities |
| PATCH | `/api/v1/devices/{id}` | 改名、房间、收藏、隐藏 |
| DELETE | `/api/v1/devices/{id}` | 从本系统移除 |
| GET | `/api/v1/device-types` | 返回已注册 TypeProfile（前端生成筛选项/图例） |
| POST | `/api/v1/devices/{id}/actions` | 统一控制 |

发现接口可返回：

```json
{
  "entity_id": "light.living_room",
  "domain": "light",
  "name": "客厅灯",
  "state": "on",
  "available": true,
  "already_added": false,
  "capabilities": ["on_off", "brightness"],
  "control_level": "full"
}
```

`control_level`：`full` | `partial` | `read_only`（便于 UI 标注「可添加但仅状态」）。

## 8. 前端：类型无关的 UI 策略

| 层级 | 策略 |
|------|------|
| 列表卡片 | 通用壳：图标（domain 默认表）+ 名称 + 主状态文案 + 快捷操作 |
| 快捷操作 | 有 `on_off` 显示开关；仅有 `raw_state` 不显示开关 |
| 详情页 | 按 `capabilities[]` 动态挂载控件（BrightnessSlider、HvacPanel…） |
| 添加页 | 发现列表 + domain 筛选 + 「仅显示可控制」开关 |
| 未支持控制 | 徽章「仅监控」，仍允许添加 |

图标映射：维护 `domain → icon` 默认表；未知 domain 用通用插头图标。

## 9. 数据模型（逻辑）

```
homes
  └── devices
        id, home_id, user_id
        entity_id          -- 唯一（同 home 下）
        domain             -- 冗余，便于筛选
        name               -- 本地显示名，空则用 HA
        room_id?
        favorite, hidden, sort_order
        created_at, updated_at

-- 不强制存 capabilities（每次用 Registry + 实时 attributes 计算）
-- 可选缓存 last_state_json 减轻 HA 压力（P2）
```

约束：

- `(home_id, entity_id)` 唯一  
- 删除设备不级联 HA

## 10. 实现分期（与功能设计对齐并细化）

| 阶段 | 发现/添加 | 类型覆盖（控制） | 展示 |
|------|-----------|------------------|------|
| **P0** | 同步发现 + 单/批量添加 + 移除 | `light`/`switch`/`input_boolean` 的 **on_off** | 全 domain **可添加**；其它 **read_only** |
| **P1** | domain 筛选、隐藏系统实体、房间 | light 亮度色温；cover；climate；button | 详情按 capability 渲染 |
| **P2** | 自动纳入可选；scene/script 入口 | media_player、vacuum 等 | 历史/分析挂钩 numeric & on_off |
| **P3** | HA device 聚合多 entity | 长尾 domain 按需 | 组合设备 |

**P0 验收补充：**

- [ ] HA 中任意已接入实体可在发现列表看到（黑名单除外）  
- [ ] 可将 light/switch 添加并开关  
- [ ] 可将 sensor 添加，仅展示数值/状态，无开关  
- [ ] 未知 domain 可添加为只读  
- [ ] 移除后可再次添加

| 配置 | 说明 |
|------|------|

## 12. 风险与原则

| 点 | 说明 |
|----|------|
| HA 是上限 | 米家某设备 HA 没有集成 → 本系统无法添加 |
| 安全 | 锁/车库门等危险类：P1 可加二次确认；能力仍受登录保护 |
| 性能 | 全量 states 可能很大：发现接口服务端过滤 + 分页 |
| 不要提前抽象过度 | P0 注册表 + 少量 mapper 即可，拒绝巨型设备中台 |

---

## 13. 总结

```
添加设备 = 从 HA 发现 entity → 纳入「我的设备」
多类型   = Domain/TypeProfile 注册表 + Capability 驱动 UI/API
扩展方式 = 加注册与映射，主流程不变
实现策略 = 先全部可添加可看，再按阶段补控制与专用 UI
```

与 [功能设计.md](./功能设计.md) 关系：功能设计管「做哪些产品能力」；本文管「多种设备如何统一添加与扩展」。
